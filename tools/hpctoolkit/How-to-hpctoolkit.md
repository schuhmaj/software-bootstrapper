# Install HPCToolkit with CUDA + OpenCL support via Spack

Tested on Ubuntu 26.04 / GCC 15.2.0 / CUDA 13.3 with Spack 1.1.1, against `hpctoolkit@2025.1.0`
and `dyninst@13.0.0`. The overlay below was generated by `spack repo create` on that version
(repo API v2.4); regenerate it if your Spack expects a different API.

The plain command

```bash
spack install -p8 hpctoolkit +cuda +opencl
```

fails twice on a current Linux distribution. Both failures and their fixes are described
below; the `spack_repo/` folder next to this file contains a ready-to-use Spack package
repository that carries the first fix.

| # | Failing package | Symptom | Fix |
| --- | --- | --- | --- |
| 1 | `dyninst@13.0.0` | `error: 'uint32_t' has not been declared` | Package repo overlay in this folder |

## TL;DR

```bash
# 1. Register the patched dyninst overlay shipped in this folder
spack repo add <this-folder>/spack_repo/bootstrapper

# 2. Install
spack install -p8 hpctoolkit +cuda +opencl
```

Verify:

```bash
$(spack location -i hpctoolkit)/bin/hpcrun -V
```

```
hpcrun: A member of HPCToolkit, version 2025.1.0
PAPI support: yes
- PAPI: 7.2.0.0
NVIDIA CUDA support: yes
- CUDA: 13.3
OpenCL support: yes
```

## Problem 1 — dyninst 13.0.0 does not build with GCC 13 or newer

`hpctoolkit` pulls in `dyninst@13.0.0`, which predates GCC 13. Since GCC 13 the libstdc++
headers no longer transitively include `<cstdint>`, so every translation unit that relied on
picking up the fixed-width integer types by accident now fails:

```
common/src/sha1.C:112:5: error: 'uint32_t' has not been declared
common/src/arch-x86.h:...: error: 'INT32_MAX' was not declared in this scope
instructionAPI/h/ArchSpecificFormatters.h:...: error: 'uint32_t' has not been declared
```

Three files need one `#include <cstdint>` each:

| File | Missing symbols |
| --- | --- |
| `common/src/sha1.C` | `uint32_t` |
| `common/src/arch-x86.h` | `INT32_MAX`, `INT32_MIN`, `UINT32_MAX` |
| `instructionAPI/h/ArchSpecificFormatters.h` | `uint32_t` |

That is exactly what `spack_repo/bootstrapper/packages/dyninst/gcc15-cstdint.patch` does
(sha256 `dae0e02e0ae4a96d0d6dd57f5a8494511ff2cda1179707119434fececa5b676b`).

### How the patch reaches Spack

Spack has no command-line flag for "apply this patch file". Patches are always declared by a
package recipe with the `patch()` directive, so the supported way to add one is a **package
repository overlay**: a small repo whose `dyninst` recipe inherits the builtin one and adds
nothing but the patch.

```
spack_repo/bootstrapper/
├── repo.yaml                                # namespace: bootstrapper
└── packages/
    └── dyninst/
        ├── package.py                       # subclasses the builtin recipe
        └── gcc15-cstdint.patch
```

```python
from spack_repo.builtin.packages.dyninst.package import Dyninst as BuiltinDyninst

from spack.package import *


class Dyninst(BuiltinDyninst):
    __doc__ = BuiltinDyninst.__doc__

    patch("gcc15-cstdint.patch", when="@13.0.0 %gcc@13:")
```

Register it once:

```bash
spack repo add <this-folder>/spack_repo/bootstrapper
spack repo list
```

```
[+] bootstrapper    v2.4    .../tools/hpctoolkit/spack_repo/bootstrapper
[+] builtin         v2.2    ~/.spack/package_repos/<hash>/repos/spack_repo/builtin
```

Check that the patch is picked up — the spec must show `patches:=dae0e02`:

```bash
spack spec dyninst@13.0.0 | head -1
```

To undo:

```bash
spack repo remove bootstrapper
```

### Why an overlay and not an edit in the builtin repo

Editing `~/.spack/package_repos/<hash>/repos/spack_repo/builtin/packages/dyninst/` works, but
that directory is a git checkout Spack manages itself — `spack repo update` will drop or
conflict with the change and the build silently breaks again. The overlay lives in this
repository instead, is version-controlled here, and survives Spack updates.

> **One-time rebuild.** The package namespace is part of the Spack DAG hash, so a `dyninst`
> coming from `bootstrapper` hashes differently from one that came from `builtin`
> (`ns=bootstrapper` → `asoadsv…` vs. `ns=builtin` → `xs5bmyh…`). If you already have
> `dyninst`/`hpctoolkit` installed from the builtin repo, adding the overlay rebuilds both
> once (~2 min). The old installs stay on disk; `spack gc` removes them.

### Upstream

This is worth upstreaming to `spack/spack-packages` — the fix is three one-line includes and
`dyninst@13.0.0` cannot be built with any GCC ≥ 13 without it. Once upstream carries it,
drop this overlay and `spack repo remove bootstrapper`.
